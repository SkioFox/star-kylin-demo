# ADR-0003 QtWebEngine Profile 隔离策略

- 状态:已接受(解评审第 5 点:共享 vs 隔离冲突)
- 日期:2026-07-21

## 问题
早期文档一处要求"会话隔离",另一处要求"统一 Cookie 共享",并笼统承诺"所有子应用共用一个全局持久化 Profile"——两者矛盾。`QWebEngineProfile` 会在其名下所有页面间共享 Cookie、存储、脚本与策略,因此"全共享"与"全隔离"不能同时成立。

## ⚠ 关键取舍(评审第 2 点):独立 Profile 会破坏全局免登
TGC 存在于**具体 Profile** 中。独立 Profile **第一次访问 CAS 通常仍要求登录**。因此以下三者**不能同时成立**:
- (a) 所有子应用一次登录后免登;
- (b) 高风险应用使用独立 Profile;
- (c) 不复制/不注入 TGC(安全要求,必须保留)。

**决策:优先保 (a)+(c),牺牲 (b) 的普适性。**

## 决策:默认统一 Profile,独立 Profile 仅限"可接受再认证"者

| 级别 | 适用子应用 | Profile 归属 | SSO 行为 |
|---|---|---|---|
| **默认统一(主)** | 绝大多数经安全评估的 web 子应用 | 共用**一个持久化 Profile** | 共享浏览器级 CAS 会话(TGC),标准流程免登 |
| **高风险独立(例外)** | **明确接受再次认证**的高敏感应用 | **独立 Profile** | 首次访问需**再登录一次**,这是有意的安全权衡,非缺陷 |

> 不再提供"按信任域自动分多 Profile 且都免登"的承诺——那与 TGC 的 Profile 绑定特性矛盾。分组只在"愿意为隔离付出再认证成本"时才做。

## 关键澄清(评审第 2 点)
- 共享 Profile 的作用是**让多个 webview 共用同一次浏览器级 CAS 会话(TGC 在 CAS 域)**,从而各子应用跑标准 `重定向→ST→后端校验` 时自动免登。
- **不是**"把 CAS Cookie 注入各子应用",也不需要子应用与 CAS 同域。
- 子应用自身的会话 Cookie 只存在于其自己域下,由其后端在校验 ST 后设置。

## 落地
- 子应用注册元数据含 `isolationLevel`(默认 `shared`,例外 `isolated`),容器据此分配 Profile。
- **M-1 必须分别实测**:同 Profile 免登、跨 Profile 免登(预期后者需再登录),据实回填结论。

## 待确认
- 哪些子应用确需独立 Profile 并接受再认证 —— 依赖安全评估与子应用清单。
- 本取舍依赖 SSO-CAS §3 身份闭环调研结论;若行内实为域集成/agent 机制,本 ADR 需随之修订。
