# CAS 单点登录与免登 —— 专题设计(修正版)

> 版本 v1.0 ｜ 2026-07-21 ｜ 关联 REQUIREMENTS §4.2
> 本版按评审第 2 点重写核心模型,取代旧稿《SSO-CAS-免登透传方案》。

## 0. 名词:REST 与 CAS 的两种登录方式

- **REST**:一种 HTTP API 设计风格(资源用 URL、操作用 HTTP 方法、多用 JSON),不是独立协议。
- **CAS 让程序登录的两种方式**,区别在"谁输账密":
  - **浏览器重定向式(CAS 默认)**:用户在 **CAS 官方登录网页**输账密,靠页面跳转 + Cookie 完成。→ 本方案默认路径。
  - **CAS REST 接口(需 CAS 服务端额外开启)**:程序用 `/cas/v1/tickets` 直接拿账密换票据,不需登录网页。银行常因安全不开放,且**REST 拿到的 TGT ≠ 浏览器里的 TGC**,不能让 webview 自动免登。→ **不作默认**。

## 1. 标准 CAS 免登模型(正确理解)

```
子应用被访问
  → 子应用重定向浏览器到 CAS/login?service=<子应用>
  → 浏览器携带 CAS 域下的 TGC(表明已登录)
  → CAS 签发一次性 ST,重定向回子应用?ticket=ST
  → 子应用【后端】调 CAS serviceValidate 校验 ST
  → 校验通过,子应用建立【自己域下】的会话
```

要点:
- **TGC 只存在于 CAS 域**,永不下发给子应用。
- **子应用是否与 CAS 同域不是关键**;跨域本就是 CAS 的设计目的。
- 每个子应用有**自己的会话**,由其后端校验 ST 后建立。

## 2. 在 QtWebEngine 里如何免登

**机制:共享浏览器级 CAS 会话,而非注入 Cookie。**

- 让参与 SSO 的 webview 共用同一个持久化 `QWebEngineProfile`(Profile 策略见 ADR-0003)。
- 该 Profile 持有 CAS 域的 TGC。于是每个 web 子应用跑**上面的标准流程**时,浏览器自动带上 TGC → CAS 直接签发 ST → 免登。
- **门户不注入、不伪造 CAS Cookie,不要求子应用与 CAS 同域。** 这与用户在一个浏览器里开多个已接入 CAS 的系统完全等价。
- ⚠ **Profile 与免登的耦合(评审第 2 点)**:TGC 存在于**具体 Profile** 中。**独立 Profile 首次访问 CAS 通常仍需登录**。因此"全局一次免登"与"高风险应用独立 Profile"不能同时成立——取舍见 ADR-0003:默认统一 Profile 保 SSO,独立 Profile 仅用于**可接受再认证**的应用。

## 3. 门户自身如何登录 + 身份闭环(⚠ 架构级待查阻塞)

### 3.1 关键缺口(评审第 1 点)
门户登录后必须**安全获知"当前用户是谁"**才能查询权限中心。但 TGC 是 CAS 域的 **HttpOnly Cookie**,**原生 Qt 侧拿不到、也无法据此安全得出身份**。仅"打开登录页拿到 TGC"**不足以**支撑"登录后展示有权限应用"这一用户场景。

### 3.2 候选方案(未定,取决于行内既有机制调研)
- **A. 门户 BFF 注册为 CAS Service(推荐)**:门户后端作为一个 CAS service,后端校验 ST 后建立**门户会话**,身份由后端持有并下发给原生外壳。
- **B. 本地回环收 ST**:经行内 CAS 批准,用本地回环地址作 service 接收 ST 再校验。
- **C. 行内既有机制**:若行内 Windows 应用免登实际靠**域集成(Kerberos/AD)或客户端 agent 持票**,则门户身份闭环应复用该机制,而非浏览器 CAS。→ **这是首要调研项。**

> 关键调研问题:**"行内现有 Windows 应用登录后打开其他系统免登,底层是怎么做的?"** 答案决定走 A/B/C 哪条,也决定 §2 的 Profile 假设是否成立。**在此定论前,不进入 M0。**

## 4. 登出:能力分层(评审第 3 点,不超出平台控制力)

平台**不能**笼统承诺"所有子应用会话全部失效"。按可保证程度分三层:

| 层 | 内容 | 谁能保证 |
|---|---|---|
| ① 本机会话清理 | 清空本机 Profile 会话 Cookie、销毁原生侧凭证 | **平台保证** |
| ② CAS TGC 失效 | 调用 CAS `/logout` 使全局 TGC 失效 | **CAS 保证** |
| ③ 子应用服务端 Session 失效 | CAS 向子应用后端回推 SLO,销毁其服务端会话 | **仅对支持 CAS SLO 的子应用保证** |

- 清理本地 Cookie 只终止本机访问,**不等于子应用服务端会话已销毁**。
- 不支持 SLO 的子应用,其服务端会话按其自身超时策略失效——需求与验收须如实反映。

## 5. 安全与合规(银行)
- 敏感会话不明文落盘(共享 Profile 加密存储或会话级不持久化)。
- CAS 交互链路 TLS,国密范围见 REQUIREMENTS §待确认。
- 不通过 JSBridge 把 CAS 凭证暴露给子应用页面;此类能力默认关闭。
- 关键节点(登录/登出/ST 校验失败)写审计。

## 6. 待确认

2. 各子应用是否支持 **CAS 后端登出通知**(决定 SLO 彻底性)。
3. 是否强制 CA 证书登录。
4. 国密是否覆盖 CAS 链路。

> 注:旧稿把"共享 CAS Cookie/是否同信任域"当作透传机制与分叉条件,属理解错误,本版已纠正——SSO 依赖的是**共享浏览器级会话 + 标准 ST 校验**,信任域只影响 Profile 分组(ADR-0003),不影响 CAS 能否免登。
