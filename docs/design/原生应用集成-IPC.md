# 原生应用集成(IPC)—— 专题设计【二期,一期仅预留接口】

> 版本 v0.1 ｜ 2026-07-21 ｜ 关联 REQUIREMENTS §2.2 ｜ 面向:已适配麒麟的原生应用

## 范围
一期**不实现**,仅在子应用容器中预留"集成协议"插槽。本文记录二期设计要点与评审纠正,避免一期做出与之冲突的假设。

## 集成协议(容器抽象)
子应用注册表统一元数据,`type` 区分承载方式:
```
type: web    → QtWebEngine 内嵌            (一期实现)
type: native → QProcess 拉起 + 统一管理     (二期)
type: embed  → 窗口嵌入                     (二期,谨慎,见下)
```

## 纠正评审第 6 点:独立进程"继承合规能力"是有限的
独立进程的原生子应用**只能自动继承**:统一入口、启动授权、部分外层审计。
**不能自动继承**:其内部的权限控制、数据安全、操作级审计。要实现这些,必须显式定义:
- **应用清单(manifest)**:能力声明、权限要求、协议版本。
- **IPC 通道**:门户 ↔ 子应用(推荐本地回环/命名管道,一次性票据领取)。
- **原生 SDK**:子应用内置,用于领票、鉴权上报、审计上报、登出响应。
- **服务端鉴权**:原生子应用后端同样须独立二次鉴权(同 web,见权限专题)。

## 纠正评审第 6 点:窗口嵌入不止 X11/Wayland 一个前提
"X11/Wayland 是能否嵌入的唯一前提"不准确。即便 X11,以下都影响可行性:
- 焦点管理、输入法(IME)、弹窗/菜单定位、DPI、多屏、崩溃隔离、目标应用窗口类型。
因此 `type: embed` 须在真机对**具体目标应用**逐一验证,不能一概而论。默认走 `type: native`(独立窗口 + 体验层统一),`embed` 仅在评估通过后个案启用。

## 免登透传(二期)
门户拉起原生子应用时,通过本地 IPC 下发**一次性 ST/票据**(用后即焚),子应用 SDK 领取后走各自后端校验建会话。避免命令行参数(进程列表可见)。
