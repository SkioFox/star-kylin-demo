### 🎨 `ui-prototype/`

| 是什么 | 怎么形成的 | 如何使用 |
|---|---|---|
| 基于 HTML/CSS/JS 的**高保真浏览器原型**,包含设计系统的全部页面、72 个状态/视口组合、38 张验收截图 | Playwright + 本地 Node 服务开发 | **不是正式程序的运行时**。只在以下情况看:①确认 UI 规格;②对照 QML 实现是否还原设计。启动:`node server.mjs` |

## 二、app/ 源码(你直接编辑的部分)

### ✍️ `app/src/` — C++ 源码

| 文件 | 职责 | 对应技术方案 |
|---|---|---|
| `main.cpp` | 进程入口:初始化 QtWebEngine、加载 Manifest、创建 AppController、进入 QML 主循环 | §5.1 启动顺序 |
| `appcontroller.{h,cpp}` | 应用总控:启动状态、登录/退出、模块分发(openModule/refreshModule/launchNative)、标签单实例、所有 QML 命令的收口 | §7.2 |
| `manifestservice.{h,cpp}` | 从 `qrc` 加载并严格校验 manifest.json,返回只读数据 | §3.2 |
| `mockauthservice.{h,cpp}` | 内存内校验 `demoA/demo-only` 和 `demoB/demo-only`,生成用户/角色 | §6.1 |
| `modulelistmodel.{h,cpp}` | 向 QML 暴露当前角色可见模块列表 | §7.2 |
| `tablistmodel.{h,cpp}` | 工作台+标签模型:单实例、切换、关闭回焦 | §6.2 |
| `urlpolicy.{h,cpp}` | 精确 Origin 校验:拦截越权导航/重定向/弹窗/资源请求/下载/证书错误 | §6.3 |
| `nativelauncher.{h,cpp}` | QProcess 固定程序拉起:校验路径→startDetached→结果反馈 | §6.4 |

### ✍️ `app/qml/` — QML 界面

## 三、app/ 构建产物(自动生成,不进 git)

### 🔨 `build-*/` — CMake 构建中间产物

| 目录 | 怎么形成的 | 对应什么 |
|---|---|---|
| `build-docker/` | Docker 容器内 `cmake -B build-docker` | 最早的 Docker 构建验证(T0A.5 打包探路) |
| `build-dockerfile-amd64/` | Docker 容器内 `cmake -B build-dockerfile-amd64` | 用 `packaging/docker/Dockerfile` 构建的 x86_64 版本 |
| `build-release-docker/` | Docker 容器内 `cmake -B build-release-docker -DCMAKE_BUILD_TYPE=Release` | Release 模式 |
| `build-verify/` | Docker 容器内独立构建 | 验证构建可复现性 |

**这些目录的共同规则:**
- 由 `cmake` 命令生成,**不需要手动创建或编辑**
- 包含 CMakeCache.txt、Makefile、编译中间文件(.o)、CPack 配置
- 已在 `.gitignore` 中排除,不进版本控制
- **删除后无影响**,重新 `cmake --build` 即可再生
- 不同 `build-*` 目录对应**不同的构建场景**(Debug/Release、不同容器),可以共存

### 📂 `staging-*/` — CMake install 安装树

| 目录 | 怎么形成的 | 对应 |
|---|---|---|
| `staging-amd64/` | `cmake --install build-docker --prefix staging-amd64` | amd64 安装树 |
| `staging-dockerfile-amd64/` | `cmake --install build-dockerfile-amd64 --prefix staging-dockerfile-amd64` | dockerfile 方案安装树 |
| `staging-script-amd64/` | `tools/build-deb.sh` 内执行 `cmake --install` | 脚本化构建安装树 |
| `staging-verify/` | `cmake --install build-verify --prefix staging-verify` | 验证构建安装树 |

**这些目录的共同规则:**
- 内含 `opt/star-kylin-demo/bin/`(二进制)、`usr/share/applications/`(桌面入口)等
- 这是 **CPack 打包前的中间态**——CPack 把 `staging/*` 的内容打包成 `.deb`
- 不在 `.gitignore` 中且**每次构建前会清空重建**
- 合并了 CMakeLists.txt 中定义的 `install()` 规则和 `CPACK_DEBIAN_*` 元数据

### 🚀 `dist/` — 最终交付物

| 路径 | 是什么 |
|---|---|
| `dist/amd64/star-kylin-demo_0.1.0_amd64.deb` | x86_64 `.deb` 安装包(476K) |
| `dist/amd64/star-kylin-demo_0.1.0_amd64.deb.sha256` | SHA-256 校验值 |
| `dist/dockerfile-amd64/star-kylin-demo_0.1.0_amd64.deb` | 另一个构建通道产出的 x86_64 `.deb`(功能等价,build-dockerfile-amd64 目录产出) |
| `dist/dockerfile-amd64/star-kylin-demo_0.1.0_amd64.deb.sha256` | 对应校验值 |

两个 `.deb` 的**二进制完全相同**(同一个 BuildID),**包元数据完全相同**(control、md5sums 逐文件一致),唯一差异是 gzip 压缩时间戳(导致最终 SHA-256 不同)。功能上**完全等价**,随便用哪个。

> 未来 ARM64 包会放在 `dist/arm64/star-kylin-demo_0.1.0_arm64.deb`

### 🧪 其他构建产物

| 目录 | 是什么 | 怎么形成的 |
|---|---|---|
| `output/qt5-smoke/` | Qt5 WebEngine 冒烟测试截图与日志 | T0A.2 验证 QtWebEngine 可用 |
| `output/qt5-smoke-min/` | 最小 Qt5 WebEngine 空窗口测试 | 同上 |
| `package-verify/` | 独立打包验证:含 `.deb` 及 `_CPack_Packages/` 中间文件 | `build-verify` 出包后拷入,验证打包流程完整性 |

## 五、常见操作速查

| 我想... | 怎么做 |
|---|---|
| 理解需求 | 读 `MVP-demo需求.md`(范围+验收) |
| 理解怎么实现 | 读 `MVP技术方案.md`(架构+安全+Profile策略) |
| 开始写代码 | 读 `MVP任务拆解.md` → 看当前任务状态 → 按技术方案的组件接口实现 |
| 看 UI 长什么样 | 读 `UI原型与功能规格.md` → 或启动 `ui-prototype/server.mjs` |
| 在 Mac 上编译 | `cmake -S app -B app/build -DBUILD_TESTING=ON && cmake --build app/build` |
| 跑测试 | `ctest --test-dir app/build --output-on-failure` |
| 出 .deb 包 | 在 Linux/麒麟上: `cd app && ./tools/build-deb.sh`(或设 STAR_KYLIN_EXPECTED_DEB_ARCH 指定架构) |
| 清除所有构建产物 | `rm -rf app/build-* app/staging-* app/dist/*`(之后重新 cmake 即可再生) |
| 查找某功能代码在哪 | C++ 在 `app/src/`,QML 在 `app/qml/`,对照技术方案 §3.2 组件职责表 |
| 理解两个 amd64 .deb 的区别 | 见本文 §三 dist/ 段——功能完全等价,随便用一个 |

## 六、重要规则

1. **`ui-prototype/` 不是正式程序**,不要把它的 HTML/CSS 嵌进 Qt WebView(除 K 线页面外)。K 线只提取图表资源,不复制原型外壳。
2. **所有 `build-*/`、`staging-*/`、`dist/`、`output/`、`package-verify/` 都是自动生成**,已在 `.gitignore` 排除或每次构建前清空。不要手动编辑里面的文件。
3. **`manifest.json` 是唯一可信源**,不要在任何代码里硬编码 URL、程序路径或角色。
4. **Intel Mac 只能编译和开发**,不能产出最终验收包;最终 `.deb` 必须来自对应架构的 Linux/麒麟构建机。
5. **冲突时优先级**:需求 > 技术方案 > 任务拆解 > 开发验证记录。
